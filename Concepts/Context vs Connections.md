# Context vs Connections

## In one sentence

[[Nate Herk]] splits a second brain's data into **context**, settled knowledge you deliberately ingest because it will still be useful in a year, and **connections**, fast-changing live data such as Slack threads, email and customer records that you leave where it lives but that the brain must know how to reach, in a set order ([26:47](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1607s)–[27:33](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1653s), [28:04](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1684s)–[28:07](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1687s), [28:17](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1697s)–[28:31](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1711s)).

## How it works

### The four C's, and the two that make up a second brain

- His AI OS videos use a four-part model: **context, connections, capabilities and cadence** ([26:41](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1601s)–[26:46](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1606s)).
- For a second brain he mostly thinks about just the **first two**, context and connections ([26:46](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1606s)–[26:51](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1611s)).
- The split comes up while he explains why he keeps ingestion under his own control. His reason is that, as he sees it, there is a big difference between some types of data ([26:36](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1596s)–[26:41](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1601s)).

| C | Place in a second brain (as this video frames it) | Timestamp |
|---|---|---|
| Context | Core. Evergreen knowledge you ingest and keep | [26:53](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1613s) |
| Connections | Core. Live data the brain can reach but doesn't store | [27:23](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1643s) |
| Capabilities | Only named here; this video doesn't expand on it | [26:46](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1606s) |
| Cadence | Only named here; this video doesn't expand on it | [26:46](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1606s) |

His one-line definitions of all four, from his public AIS-OS repo, are under *Beyond the source*.

### Context: settled knowledge you ingest

- Context covers what the business has done and what is happening in it now ([26:53](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1613s), [27:20](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1640s)–[27:22](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1642s)).
- **His example is quarterly project files.** His main brain (Herk2) has a folder of the quarter's projects. The captions call them "OTAs", and he explains the term as meaning the projects for the quarter ([27:01](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1621s)–[27:03](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1623s)). *(The exact term is unclear in the captions.)*
- There are Q1 files and Q2 files. Opening one shows the decisions that were made and the current status of each item ([27:05](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1625s)–[27:11](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1631s)).
- They count as context because they are **locked-in decisions**, the commitments for the quarter. He still keeps the statuses up to date ([27:12](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1632s)–[27:20](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1640s)). So context isn't frozen. The decision is fixed and the file is worth keeping, while its status fields change.
- Other stores in the video that fit his definition of context *(the video doesn't label these as context; the grouping is this note's)*:
  - The Level 1 **decision log**, where CLAUDE.md tells Claude to append each big decision with its date ([06:08](https://www.youtube.com/watch?v=DTCyvo6cC54&t=368s)–[06:14](https://www.youtube.com/watch?v=DTCyvo6cC54&t=374s)).
  - A [[CLAUDE.md as a Router|CLAUDE.md routing rule]] pointing to the folder of quarter-one priorities ([04:48](https://www.youtube.com/watch?v=DTCyvo6cC54&t=288s)).
  - His transcript wikis for YouTube videos and meetings ([08:36](https://www.youtube.com/watch?v=DTCyvo6cC54&t=516s)–[08:41](https://www.youtube.com/watch?v=DTCyvo6cC54&t=521s)). See [[LLM Wiki]].

### Connections: live data you reach but don't ingest

- Connections are real data that **isn't as evergreen**. It keeps changing ([27:25](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1645s)–[27:29](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1649s)).
- His examples are Slack threads, email and customer data ([27:31](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1651s)–[27:33](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1653s)).
- **Don't ingest it.** Inside the brain it turns into noise ([27:33](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1653s)–[27:37](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1657s)), and you would have to clear out old items every month ([27:39](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1659s)–[27:41](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1661s)).
- **But don't cut the brain off from it.** It should still be able to go and fetch that data when needed ([28:04](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1684s)–[28:07](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1687s)).
- Reachability depends on routing. From Level 1: Claude won't search your whole project on its own, and it can't find something if it doesn't know where it lives ([05:03](https://www.youtube.com/watch?v=DTCyvo6cC54&t=303s)–[05:13](https://www.youtube.com/watch?v=DTCyvo6cC54&t=313s)). *This note's inference, not something he says about live sources:* by the same logic, if the router never mentions a live source, the agent is unlikely to reach for it.

### The sorting question and the one-year test

- Whenever you add data to the project, decide which kind it is. Evergreen, holistic material goes one way. Material that will change next week goes the other ([27:53](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1673s)–[28:02](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1682s)).
- His working definition of the brain itself: **things he doesn't expect to ever delete** ([27:41](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1661s)–[27:45](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1665s)).
- **The one-year test:** would it still help to have this memory stored a year from now? If yes, it belongs in the brain. If not, it only adds noise ([27:47](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1667s)–[27:51](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1671s)).

Put together as a quick triage, using only the video's own criteria:

| Question | If yes | Source |
|---|---|---|
| Will this still be useful in a year? | Context. Ingest it | [27:47](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1667s) |
| Is it a settled decision or commitment (with a status you'll update)? | Context. Ingest it | [27:14](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1634s) |
| Will it change by next week? | Connection. Don't ingest; make sure it's reachable | [28:00](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1680s)–[28:07](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1687s) |
| Would you have to prune it every month? | Connection. Don't ingest | [27:39](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1659s) |

### Reaching connections: look in a set order

His example question is what he and John discussed last week about quarterly project number seven, captioned "OTA number seven" ([28:09](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1689s)–[28:14](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1694s)). The brain works down a ladder and only moves to the next rung if the current one doesn't have the answer ([28:19](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1699s)–[28:26](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1706s)):

| Step | Where it looks | Kind of data | Timestamp |
|---|---|---|---|
| 1 | The quarterly project file for that project | Context | [28:17](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1697s) |
| 2 | The wiki and the meeting transcripts, named together as one fallback, to see what was said | Context (he ingests meeting transcripts weekly, [26:28](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1588s)) | [28:21](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1701s)–[28:25](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1705s) |
| 3 | ClickUp itself, pulling the actual conversation between him and John | Connection (live) | [28:27](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1707s)–[28:31](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1711s) |

*Read as a pattern (this note's reading, not his words):* the order runs from curated, stable sources to live, raw ones, with the live system as the last resort. The build steps are in [[Tiered Lookup Routing]]. Its starter splits his middle step into two tiers, wiki first and then meeting transcripts. That split is the vault's suggestion, not something he says.

### His definition of a working second brain

- Having to fall back to ClickUp doesn't stop it being a second brain. He can ask a vague question and it knows **where to look and in what order** to find real-time data, then gives him the answer ([28:33](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1713s)–[28:41](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1721s)).
- The question he asks himself about any setup: does it understand where his data lives, does it know where to look, and does it return accurate answers? ([28:42](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1722s)–[28:47](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1727s))
- This matches how the video opens. The real test is whether your agent, and you, can find something again ([02:13](https://www.youtube.com/watch?v=DTCyvo6cC54&t=133s)). How data will be retrieved should decide how it goes in ([02:39](https://www.youtube.com/watch?v=DTCyvo6cC54&t=159s)–[02:44](https://www.youtube.com/watch?v=DTCyvo6cC54&t=164s)). See [[Design for Retrieval]].

### Why the split makes him cautious about always-on brains

- The distinction comes up in the Level 5 section. A tool like [[GBrain]] is always on and keeps syncing, refreshing memories and adding more ([25:44](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1544s)–[25:48](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1548s)). Running that from Claude Code would mean setting up and managing the cron jobs yourself ([25:52](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1552s)–[25:58](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1558s)).
- His worry is the **too-much-context problem**: past some point, extra context does more harm than good ([26:10](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1570s)–[26:22](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1582s)).
- So he keeps **full control of what the brain ingests** ([26:23](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1583s)). A skill gathers the week's meeting transcripts, and he and Claude work out together where each piece belongs before ingesting it ([26:28](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1588s)–[26:35](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1595s)). *(The captions are garbled in the middle of that sentence.)*
- He ties that preference for control directly to the context/connections distinction ([26:36](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1596s)–[26:51](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1611s)). See [[Always-On Brain OS]].

### Other sources: the plumbing behind "connections"

*Everything above comes from [[Nate Herk - Every Level of a Claude Second Brain]]. The sources below add the mechanics of reaching live data, and two of them (Chase AI and Matt Wolfe) challenge his don't-ingest rule; see the "Where sources disagree" section.*

**Keep the words apart.** Nate's *connections* are a kind of data: live, changing, fetched rather than stored. Other creators use *applications* or *connectors* for the mechanism that reaches an app. The ideas fit together but sit at different layers.

| Term | Source | What it names |
|---|---|---|
| Connections | [[Nate Herk - Every Level of a Claude Second Brain]] | Volatile data that stays reachable but isn't ingested ([27:25](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1645s)–[28:07](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1687s)) |
| Applications (the A in ARMS) | [[Jay E - The ARMS Framework for a Claude Agentic OS]] | The layer that connects the agent to your apps, usually through a CLI, an API or an MCP server ([18:34](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1114s), [19:06](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1146s)–[19:30](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1170s)) |
| Connectors | [[Simon Pittman - Set Up Claude Cowork]] | The Cowork settings page where tools such as Notion, Gmail and Google Calendar are attached ([20:36](https://www.youtube.com/watch?v=pl90LATQlHI&t=1236s)–[20:57](https://www.youtube.com/watch?v=pl90LATQlHI&t=1257s)) |
| MCP servers | [[Nate Herk - 32 Tricks to Level Up Claude Code]], [[Anthropic - What Is Claude Managed Agents]] | One protocol for the plumbing. Nate warns about its context cost ([11:24](https://www.youtube.com/watch?v=jqoFP9QapXI&t=684s)); Anthropic's demo posts to Slack and Asana through it ([02:07](https://www.youtube.com/watch?v=NLWiIj47IdI&t=127s)–[02:13](https://www.youtube.com/watch?v=NLWiIj47IdI&t=133s)) |

Setup across Claude surfaces is covered in [[Connecting Claude to External Tools]], and the ARMS model in [[Agentic OS]].

#### Jay E: connectors grow in three steps

[[Jay E]] puts applications last of his four layers. He learns them after skills, memory and routines ([04:27](https://www.youtube.com/watch?v=8NSyI-npJCU&t=267s)–[04:39](https://www.youtube.com/watch?v=8NSyI-npJCU&t=279s)), because real work with agents means reaching the apps where it happens ([18:34](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1114s)–[18:40](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1120s)).

1. **Level 1:** browse the connectors directory in the desktop app, under Customize then Connectors ([18:42](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1122s)–[18:51](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1131s)).
2. **Level 2:** he finds the directory inefficient, so he lets Claude Code find connectors itself. His search-connectors skill checks the web for an official connector first, then for community-made ones ([18:53](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1133s)–[19:30](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1170s)). Before setting up a recommended community repo, he has Claude Code check that it's safe ([19:45](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1185s)–[19:51](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1191s)).
3. **Level 3:** build your own. He used Matt Van Horn's CLI Printing Press to make connectors for MyFitnessPal and Skool, which had none ([19:53](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1193s)–[20:21](https://www.youtube.com/watch?v=8NSyI-npJCU&t=1221s)).

He never says which data should be copied in and which fetched. His layer is about access, not about a one-year test. *(This note's observation.)*

#### Simon Pittman: connect every tool, then map the big ones

- **Connect widely.** [[Simon Pittman]]'s Cowork has Notion, Slack, Supabase, Vercel, Make.com, Google Calendar, Google Drive and Gmail connected ([20:42](https://www.youtube.com/watch?v=pl90LATQlHI&t=1242s)–[20:57](https://www.youtube.com/watch?v=pl90LATQlHI&t=1257s)). He recommends adding every tool you use; each one asks for permission ([23:37](https://www.youtube.com/watch?v=pl90LATQlHI&t=1417s)–[23:44](https://www.youtube.com/watch?v=pl90LATQlHI&t=1424s)).
- **Set permissions per tool.** In Gmail you choose what to allow. Notion has many permissions, each of which can be allowed, need approval or be blocked ([24:24](https://www.youtube.com/watch?v=pl90LATQlHI&t=1464s)–[24:41](https://www.youtube.com/watch?v=pl90LATQlHI&t=1481s)). He also tells Claude to only ever create email drafts and to record that rule in its memory or instructions ([26:18](https://www.youtube.com/watch?v=pl90LATQlHI&t=1578s)–[26:38](https://www.youtube.com/watch?v=pl90LATQlHI&t=1598s)). His global instructions already forbid sending without his check ([26:49](https://www.youtube.com/watch?v=pl90LATQlHI&t=1609s)–[26:59](https://www.youtube.com/watch?v=pl90LATQlHI&t=1619s)).
- **Not every connected tool is volatile.** He treats Notion differently from email and calendar. It holds context (projects, knowledge, meeting notes), not just messages and meetings ([27:41](https://www.youtube.com/watch?v=pl90LATQlHI&t=1661s)–[28:18](https://www.youtube.com/watch?v=pl90LATQlHI&t=1698s)). *This note's reading:* a connection isn't always volatile. It can be a stable store that simply lives outside the brain.
- **Map the connected tool.** His first Notion search took several attempts ([28:51](https://www.youtube.com/watch?v=pl90LATQlHI&t=1731s)–[28:56](https://www.youtube.com/watch?v=pl90LATQlHI&t=1736s)). His method is to have Claude read a top-level page linking all his databases and build a context map from it. On screen he drops in a `my-context-map.md` he had made that way earlier, then asks Claude for updated global instructions so it's read every session ([29:20](https://www.youtube.com/watch?v=pl90LATQlHI&t=1760s)–[30:05](https://www.youtube.com/watch?v=pl90LATQlHI&t=1805s), [30:14](https://www.youtube.com/watch?v=pl90LATQlHI&t=1814s)). The next query found the right database immediately ([30:33](https://www.youtube.com/watch?v=pl90LATQlHI&t=1833s)–[30:38](https://www.youtube.com/watch?v=pl90LATQlHI&t=1838s)). He adds that the map stops Claude burning tokens searching ([31:03](https://www.youtube.com/watch?v=pl90LATQlHI&t=1863s)–[31:11](https://www.youtube.com/watch?v=pl90LATQlHI&t=1871s)). Build it with [[Build a Context Map for a Connected Tool]]; use it as a lookup tier with [[Tiered Lookup Routing]].
- **Schedules use the same connections.** His scheduled tasks run on his instructions, connectors and context ("contacts" in the captions) ([41:35](https://www.youtube.com/watch?v=pl90LATQlHI&t=2495s)–[41:43](https://www.youtube.com/watch?v=pl90LATQlHI&t=2503s)). His weekly briefer reads his About Me files, then searches Notion, Gmail and Calendar ([42:01](https://www.youtube.com/watch?v=pl90LATQlHI&t=2521s)–[42:22](https://www.youtube.com/watch?v=pl90LATQlHI&t=2542s)).

#### Nate Herk (32 tricks): connections cost context

- In [[Nate Herk - 32 Tricks to Level Up Claude Code]], Nate points to `/context`. It shows what is using your tokens, MCP servers included, as percentages, so you can diagnose a bloated session ([01:49](https://www.youtube.com/watch?v=jqoFP9QapXI&t=109s)–[02:07](https://www.youtube.com/watch?v=jqoFP9QapXI&t=127s)).
- He says MCP servers load their full tool definitions into the context window. When tokens are tight, a direct API endpoint can be leaner ([11:24](https://www.youtube.com/watch?v=jqoFP9QapXI&t=684s)–[11:41](https://www.youtube.com/watch?v=jqoFP9QapXI&t=701s)). His example: if a project only needs to read one Notion database, hardcode that one endpoint instead of exposing every Notion function ([11:41](https://www.youtube.com/watch?v=jqoFP9QapXI&t=701s)–[11:56](https://www.youtube.com/watch?v=jqoFP9QapXI&t=716s)).
- *Current Claude Code loads MCP tools differently; see "Beyond the source" below.*

#### Anthropic's Managed Agents demo: fetch live, remember the change

- In [[Anthropic - What Is Claude Managed Agents]], a pricing agent searches the web for current pricing pages on each run ([01:54](https://www.youtube.com/watch?v=NLWiIj47IdI&t=114s)–[01:59](https://www.youtube.com/watch?v=NLWiIj47IdI&t=119s)).
- It reads a memory store before starting, to check what it found last week, and stores what changed when it finishes ([02:15](https://www.youtube.com/watch?v=NLWiIj47IdI&t=135s)–[02:23](https://www.youtube.com/watch?v=NLWiIj47IdI&t=143s)). The next report therefore gives changes instead of repeating the same pricing data ([02:23](https://www.youtube.com/watch?v=NLWiIj47IdI&t=143s)–[02:30](https://www.youtube.com/watch?v=NLWiIj47IdI&t=150s)).
- An incident coordinator checks past incidents in memory and recognises a repeat of a DNS problem caused by a misconfigured TTL. The next similar alert starts with that context ([03:08](https://www.youtube.com/watch?v=NLWiIj47IdI&t=188s)–[03:26](https://www.youtube.com/watch?v=NLWiIj47IdI&t=206s)).
- *This note's reading:* the raw, volatile data (today's prices, today's alert) is fetched live, as Nate advises. The derived findings (what changed, what caused an incident) are kept. That applies the one-year test to findings rather than to whole sources.

#### Matt Wolfe: people and journals inside the brain, ingested hourly

[[Matt Wolfe - Second Brain Wiki with Journal and CRM]] goes against both of Nate's rules. He builds in [[OpenAI Codex]], not Claude.

- **A personal CRM in the vault.** He wants to remember conversations with people he meets ([01:33](https://www.youtube.com/watch?v=yke4fLQUsh4&t=93s)). He stores how and where they met, what they discussed, and contact details such as email, phone and address ([01:46](https://www.youtube.com/watch?v=yke4fLQUsh4&t=106s)), with one file per person ([23:12](https://www.youtube.com/watch?v=yke4fLQUsh4&t=1392s)).
- **Whole journal chats in the vault.** Replies draw on the wiki, past entries and the CRM ([22:47](https://www.youtube.com/watch?v=yke4fLQUsh4&t=1367s)). His diagram also has meeting notes flowing in ([03:18](https://www.youtube.com/watch?v=yke4fLQUsh4&t=198s)).
- **Unattended ingest.** An hourly job processes whatever lands in raw/ ([29:34](https://www.youtube.com/watch?v=yke4fLQUsh4&t=1774s)). Nate wants full control over what goes in ([26:23](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1583s)).
- For a reconciliation, see point 5 of *Where sources disagree*; [[Add a Journal and Personal CRM to a Second Brain]] builds it into its person template.

## When to use it — and when not to

**Sorting the examples the video gives**

*He classifies the quarterly project files, Slack threads, email and customer data himself, and uses ClickUp as the live last step. The decision log, meeting transcript and YouTube transcript rows are this note's classification, using his criteria.*

| Data | Context or connection | Timestamp |

**Use the split when**
- You are deciding whether to ingest a new data source. He says to think about which kind it is whenever you add data to the project ([27:53](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1673s)).
- The brain answers well about plans but badly about "what happened last week". *This diagnostic is this note's inference from his rule:* the likely fix is a missing connection, not more ingestion ([28:04](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1684s)–[28:07](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1687s)).
- You are setting up a shared team brain. There too, the goal is to keep the shared store useful instead of noisy, with process owners keeping their own docs current ([30:03](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1803s)–[30:09](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1809s)).
- You are adding a connector. Decide whether the tool is a volatile stream, like email and calendar, or a context store that happens to live elsewhere, the way Simon Pittman describes Notion ([28:09](https://www.youtube.com/watch?v=pl90LATQlHI&t=1689s)–[28:18](https://www.youtube.com/watch?v=pl90LATQlHI&t=1698s)). A context store deserves a map and an early place in the lookup order ([[Build a Context Map for a Connected Tool]]). *(Applying the split to connectors is this note's suggestion.)*
- Someone suggests copying a whole domain into the brain, as Chase AI suggests for sales data ([15:12](https://www.youtube.com/watch?v=HRw-vP0j8OM&t=912s)). Run the one-year test per record before agreeing (see *Where sources disagree*).

**Pitfalls**
- **Ingesting volatile data** creates noise and a monthly clean-up job ([27:37](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1657s)–[27:41](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1661s)).
- **Neither ingesting nor connecting it.** He requires that the brain can still fetch what it doesn't store ([28:05](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1685s)). Without a route, questions about recent events fail.
- **Letting ingestion run unattended** risks the too-much-context problem ([26:17](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1577s)–[26:22](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1582s)). He does say the always-on route makes sense if you run agents "offline" (as captioned; likely meaning unattended), have a lot of data, and need several [[Hermes Agent]] instances kept in sync ([29:25](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1765s)–[29:31](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1771s)).
- **A tension the video leaves open.** Early on he lists ClickUp threads with notes and meeting recordings as things you save into a second brain and ingest ([01:59](https://www.youtube.com/watch?v=DTCyvo6cC54&t=119s)–[02:08](https://www.youtube.com/watch?v=DTCyvo6cC54&t=128s)). Later he says not to ingest volatile data such as Slack threads, email and customer data, and uses ClickUp as the live source the brain queries last ([27:29](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1649s)–[27:37](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1657s), [28:27](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1707s)). The video doesn't reconcile the two. One way to reconcile them (this note's reading, not his) is to apply his one-year test to each item rather than to a whole tool ([27:47](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1667s)).

For checking a whole setup folder by folder, see [[Second Brain Pain-Point Audit]].

## Where sources disagree

**1. Copy a domain's data into the brain, or leave it where it lives?**
- [[Nate Herk - Every Level of a Claude Second Brain]]: don't ingest volatile data such as Slack threads, email or customer data. It becomes noise you'd have to prune every month, so fetch it live instead ([27:29](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1649s)–[27:41](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1661s), [28:04](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1684s)).
- [[Chase AI - The Agentic OS Setup for Claude Code]]: whichever folder you make the vault should hold at least a copy of all the data for each domain the OS helps with. His example is all your sales data ([15:03](https://www.youtube.com/watch?v=HRw-vP0j8OM&t=903s)–[15:14](https://www.youtube.com/watch?v=HRw-vP0j8OM&t=914s)). He doesn't say how to keep that copy current or what to prune. Yet his own dashboard reads items live from Google Calendar, which is the connections pattern ([23:59](https://www.youtube.com/watch?v=HRw-vP0j8OM&t=1439s)).
- *One way to reconcile them (this note's, not either creator's):* apply the one-year test to each record, not to a whole domain. Closed deals and past sales totals pass it and can be copied in. Open pipeline status fails it and should stay live.

**2. Should volatile state go into a memory file?**
- Nate keeps only what he'd still want a year from now ([27:47](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1667s)).
- [[Simon Pittman - Set Up Claude Cowork]] has Claude append to a `memory.md`. It's a log of preferences, decisions and context recorded after each session ([14:55](https://www.youtube.com/watch?v=pl90LATQlHI&t=895s)–[15:16](https://www.youtube.com/watch?v=pl90LATQlHI&t=916s), [15:32](https://www.youtube.com/watch?v=pl90LATQlHI&t=932s)–[15:42](https://www.youtube.com/watch?v=pl90LATQlHI&t=942s)). After triaging overdue Notion tasks, Claude updated that memory with what it had learned about his projects and products ([31:49](https://www.youtube.com/watch?v=pl90LATQlHI&t=1909s)–[31:55](https://www.youtube.com/watch?v=pl90LATQlHI&t=1915s)). He gives no pruning rule. *The risk is this note's inference:* project status can build up in the file, which is the kind of noise Nate warns about.
- [[Anthropic - What Is Claude Managed Agents]] takes a middle path. Each run stores what changed, not the full data ([02:19](https://www.youtube.com/watch?v=NLWiIj47IdI&t=139s)–[02:30](https://www.youtube.com/watch?v=NLWiIj47IdI&t=150s)).

**3. Is an MCP connection too costly to keep attached?**
- [[Nate Herk - 32 Tricks to Level Up Claude Code]]: MCP servers put their full tool definitions into context, so use a direct endpoint when tokens are tight ([11:24](https://www.youtube.com/watch?v=jqoFP9QapXI&t=684s)–[11:56](https://www.youtube.com/watch?v=jqoFP9QapXI&t=716s)).
- [[Simon Pittman - Set Up Claude Cowork]] keeps the Notion MCP server connected ([28:37](https://www.youtube.com/watch?v=pl90LATQlHI&t=1717s)–[28:45](https://www.youtube.com/watch?v=pl90LATQlHI&t=1725s)). He cuts token use a different way, with a context map so Claude doesn't search blindly ([31:03](https://www.youtube.com/watch?v=pl90LATQlHI&t=1863s)–[31:11](https://www.youtube.com/watch?v=pl90LATQlHI&t=1871s)).
- This note's *Beyond the source* recommends MCP servers for connections, and current Claude Code docs change the cost picture Nate describes. See below.

**4. Not a disagreement: "connectors" vs "connections".** Jay's applications layer and Simon's connectors are *how* a brain reaches Nate's connections. Keep the terms separate. A connector can also reach stable context, as Simon's Notion does ([28:09](https://www.youtube.com/watch?v=pl90LATQlHI&t=1689s)–[28:18](https://www.youtube.com/watch?v=pl90LATQlHI&t=1698s)), so "connected" doesn't mean "volatile".

**5. Personal data and unattended ingest.**

| Question | [[Nate Herk - Every Level of a Claude Second Brain]] | [[Matt Wolfe - Second Brain Wiki with Journal and CRM]] |
|---|---|---|
| Store records about people? | No. Customer data is volatile, so reach it live ([27:31](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1651s)) | Yes. One file per person, with contact details and how you met ([23:15](https://www.youtube.com/watch?v=yke4fLQUsh4&t=1395s)) |
| Store personal reflections? | Not discussed. His test is whether it's still useful in a year ([27:47](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1667s)) | Every journal chat is saved in full ([22:03](https://www.youtube.com/watch?v=yke4fLQUsh4&t=1323s)) |
| Who decides what goes in? | He does, to avoid too much context ([26:17](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1577s), [26:23](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1583s)) | An hourly job processes everything clipped into raw/ ([29:34](https://www.youtube.com/watch?v=yke4fLQUsh4&t=1774s)) |
| Raises privacy? | Yes. Data processed through Claude goes to Anthropic ([21:33](https://www.youtube.com/watch?v=DTCyvo6cC54&t=1293s)) | No |

*One way to reconcile them (this note's, not either creator's):* apply the one-year test field by field, not person by person. Keep relationship history, point to live sources for details that change, and let scheduled ingest touch raw/ only, never the private layers.

## Beyond the source

*None of this comes from the videos. Each item was checked against the linked page.*

- **His four C's definitions.** Nate's public AIS-OS repo sets out the framework with a one-line job and a test for each C. Context: it knows your business, and a fresh session can answer business questions without browsing. Connections: it reaches your stuff, answering about calendar and tasks from live data without manual pasting. Capabilities: it knows how to do the work, so a short phrase triggers a multi-step workflow that produces an artifact. Cadence: it runs without being asked, for example a brief lands in your inbox while your laptop is closed. **Build order:** context first and non-negotiable, connections and capabilities in parallel, cadence last, because workflows that don't work manually shouldn't be automated. The repo itself doesn't say which C's make up a "second brain"; that pairing comes from the video. Verified: [nateherkai/AIS-OS on GitHub](https://github.com/nateherkai/AIS-OS).
- **The same idea in Anthropic's context-engineering guidance.** Anthropic's article (2025-09-29) describes "just in time" context. The agent holds lightweight references (file paths, stored queries, web links) and loads the data at runtime with tools, instead of loading everything up front. It says Claude Code works as a hybrid: CLAUDE.md goes into context at the start, and tools like glob and grep fetch files when needed. This lines up with the video. Curated context is loaded or routed ahead of time, while connections stay as references that are resolved on demand. Verified: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- **Evidence behind the "too much context" worry.** The same Anthropic article describes *context rot*: a model's ability to recall information goes down as the number of tokens in context goes up, degrading gradually rather than failing at a fixed point. Chroma's study (2025-07-14) tested 18 models and found performance falls as input length grows. Even one distractor lowered accuracy, and more distractors made it worse. Stale, near-duplicate items ingested from volatile sources are the kind of material that can act as distractors. Verified: [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [Chroma — Context Rot](https://www.trychroma.com/research/context-rot).
- **How to wire up connections in Claude Code: MCP servers.** Claude Code connects to external tools and data through MCP. The docs give examples including Slack, Gmail, Notion, Asana, HubSpot and databases. You add a remote server with `claude mcp add --transport http <name> <url>`. The scope can be local (the default, just you in this project), project (saved to `.mcp.json` at the project root and shared through version control) or user (all your projects). Verified: [Claude Code docs — MCP](https://code.claude.com/docs/en/mcp).
- **ClickUp, his last-step connection, has an official MCP server.** It is hosted at `https://mcp.clickup.com/mcp`, uses OAuth, and ClickUp's own setup page gives the Claude Code command `claude mcp add --transport http clickup https://mcp.clickup.com/mcp`. Verified: [ClickUp developer docs — MCP server setup](https://developer.clickup.com/docs/connect-an-ai-assistant-to-clickups-mcp-server-1).
- **Auto memory and the one-year test.** [[Claude Code Auto Memory]] is stored per project outside the repo, at `~/.claude/projects/<project>/memory/`. A `MEMORY.md` index is loaded into every session (the first 200 lines or 25KB), and topic files are read when needed. Claude decides what to save based on whether it would help in a future conversation. One of its memory types, `reference`, records *where to find information outside the project, such as an issue tracker or dashboard*. That is effectively a stored pointer to a connection, not a copy of the data. Memory files aren't removed by transcript clean-up and stay until you or Claude edits or deletes them, so volatile facts that end up there will build up unless someone prunes them. The video shows a memory.md inside his example project folder; Claude Code's own store lives in the home-directory path above. Verified: [Claude Code docs — memory](https://code.claude.com/docs/en/memory).
- **Claude Code no longer loads MCP tool definitions up front by default.** Claude Code's docs say tool search is on by default. MCP tool definitions are held back until Claude needs them, and only tool names and server instructions load at session start, so adding more servers has little effect on the context window. Tool search is off if `ENABLE_TOOL_SEARCH=false` is set, if `ANTHROPIC_BASE_URL` points at a non-first-party host, or if `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` is set. It needs Sonnet 4.5, Haiku 4.5, Opus 4.5 or a later model. What a tool *returns* still costs context. Claude Code warns when a single MCP tool result is over 10,000 tokens, and caps results at 25,000 tokens by default (`MAX_MCP_OUTPUT_TOKENS`). *This note's view:* the tip in [[Nate Herk - 32 Tricks to Level Up Claude Code]] to prefer endpoints over MCP ([11:24](https://www.youtube.com/watch?v=jqoFP9QapXI&t=684s)) assumes tools load up front. Today, check `/context` before swapping a server for raw endpoints, and watch the size of live pulls more than the tool list. Verified: [Claude Code docs — MCP](https://code.claude.com/docs/en/mcp).
- **Managed Agents memory stores have limits and a poisoning risk.** A memory store is a workspace-scoped collection of text documents. It is mounted as a directory in the agent's sandbox and read and written with ordinary file tools. A store holds up to 10,000 memories of up to 100 kB each. The docs recommend many small, focused files, and deleting stale memories or running a *dreaming* session that consolidates content into a new store. Stores attach read-write by default. The docs warn that a prompt injection in fetched web content or tool output could write malicious memories that later sessions treat as trusted, and advise `read_only` for reference material. That warning applies to any "fetch live, remember the change" design, like the pricing agent above. Verified: [Claude Platform docs — Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory).
- **Illustrative CLAUDE.md block (not from the video).** A way to write the split and the lookup order into a router. CLAUDE.md is plain-markdown instructions loaded each session ([docs](https://code.claude.com/docs/en/memory)), and the live step assumes an MCP server as above ([docs](https://code.claude.com/docs/en/mcp)). Paths follow the vault's shared starter layout ([[Build a Level 1 Second Brain]] plus `wikis/` from [[Ingest Sources into an LLM Wiki]]). The lookup order splits his middle step into two:

  ```markdown
  ## What goes in this brain
  - Ingest (context): projects/priorities.md (quarterly projects with decisions + statuses),
    decisions.md (dated), wikis/ (curated meeting + video transcripts).
  - Do NOT ingest (connections): Slack, email, customer records, ClickUp threads.
    Query them live instead.
  - Before saving anything, ask: will this still be useful in a year?
    If not, don't store it; note where it can be found instead.

  ## Lookup order for "what did we discuss about project X?"
  1. projects/priorities.md, then that project's projects/<name>/README.md
  2. wikis/<name>/index.md, then linked pages
  3. wikis/meetings/ (one page per meeting)
  4. ClickUp via the `clickup` MCP server (live data), only if 1-3 have no answer
  ```
